# v1.8.0 Design — Bucket Templates, Account Safety, and UX Depth

Date: 2026-07-29
Branch: `release/1.8.0/bucket-templates-ux`
Status: approved for implementation (autonomous session; the requesting user pre-authorized
the full brainstorm → design → implement → test → release cycle in the task prompt).
Every "current state" claim below was verified against source by exploration agents on
2026-07-29 at commit `d995e0e` (v1.7.4).

## Scope

Eleven user-requested features, implemented in phases, each phase independently tested,
committed, and pushed through the branch gate ladder:

| # | Feature | Phase |
|---|---------|-------|
| 4 | Numeric inputs: 0 must be placeholder, not value | 1 |
| 2 | Logout confirmation modal + loader | 2 |
| 9 | Language/theme persisted per user | 3 |
| 7 | Split dense settings page into subpages | 4 |
| 3 | Delete account: danger dialog + email/password re-entry | 5 |
| 8 | Privacy/analytics settings must be real, not decorative | 6 |
| 1 | Bucket as reusable template; reorder without "(copy)" duplication | 7 |
| 5 | Per-component loading skeletons | 8 |
| 6 | OS notification propagation + permission prompts | 9 |
| 10 | Per-page tutorial overlays with "don't show again" | 10 |
| 11 | Catchier icons, easier UX | 11 |

Ordering rationale: small isolated fixes first (1–3), then the settings split (4) so the
account-safety and privacy work (5–6) lands in its final home, then the large domain
refactor (7), then cross-cutting UI systems (8–10), then polish informed by browser UAT (11).

## Non-goals

- Migrating the shipping v1.3 bucket-as-live-order group flow to order sessions wholesale.
  Sessions become the *reorder* path; the existing collaborate/place flow stays intact with
  its critical e2e coverage.
- Background (app-closed) push via FCM. Requires a VAPID key, `google-services.json`, and
  APNs assets that only the project owner can create in the Firebase console. This release
  ships foreground OS-tray mirroring with permissions; FCM prerequisites are documented.
- Shipping product analytics to any vendor. No vendor is approved (telemetry README
  integration boundary); consent will gate a real, local, privacy-safe diagnostics sink.
- iOS build validation (EXC-5 — no macOS environment; recorded honestly, never claimed).

## Phase 1 — Numeric inputs: zero as placeholder (item 4)

**Current state (verified).** Exactly 5 `type="number"` inputs exist, all raw `<input>`:
VAT/service/delivery in `bucket-pricing-panel.component.tsx:55-101`, unit price in
`bucket-editor.container.tsx:118-130`, custom-item price in
`custom-item-panel.component.tsx:77-137`. The pricing panel's `toBasisPoints`/`toMinorUnits`
coerce `''` → `0` (`Number('') === 0`), so clearing a field snaps back to `0` and typing
appends after it ("014"). The custom-item panel already holds a *string* draft and does not
exhibit the clobbering — that is the model to generalize.

**Design.** New shared primitive `src/shared/ui/numeric-field/` (component + container +
hook + index, per file-suffix rules):

- Props: `id?, label, value: number, onValueChange(next: number), min?, max?, step?,
  decimalPlaces?, placeholder ("0"), disabled?`. All copy via props (shared UI reads no i18n).
- Internal draft string state in `use-numeric-field.hook.ts`: displays `''` when the
  numeric value is 0 **and** the user has not typed "0" deliberately; placeholder shows the
  zero. `inputMode="decimal"` for mobile keyboards.
- On change: empty draft → emit 0 (state stays 0, display stays empty); invalid → keep
  previous; valid → clamp to [min, max] and emit. On blur: normalize draft to the canonical
  value (or empty for 0).
- Callers keep their unit conversions (percent ↔ basis points, major ↔ minor units).

All 5 inputs migrate to it. Explicit `htmlFor`/`id` labeling replaces implicit labels.

**Tests.** New `tests/components/NumericField.test.tsx` (empty-display for 0, typing "14"
yields 14 not 014, clamping, blur normalization). Update
`GroupOrderComponents.test.tsx:120-133` (negative entry still clamps to 0; the *display*
assertion changes) and `bucket-pricing.spec.ts:81-90,124-126` (fill-by-label still works;
values assert `'14'` etc. — unchanged semantics).

## Phase 2 — Logout confirmation + loader (item 2)

**Current state (verified).** Logout is one icon button rendered twice
(`app-layout.container.tsx:113,133`), fires `void logout()` immediately; `ConfirmDialog`
(`src/shared/ui/confirm-dialog/`) has no busy state.

**Design.** Add optional `busy?: boolean` to `ConfirmDialog` (disables both buttons,
swaps confirm label for a spinner glyph + `aria-busy`). In `use-app-layout.hook.ts`: new
`confirmingLogout` / `loggingOut` state, `requestLogout` / `cancelLogout` /
`confirmLogout` (awaits session `logout()`, redirect happens declaratively via the auth
subscription and `ProtectedRoute`). Dialog rendered once in `app-layout.container.tsx`.
Both logout buttons call `requestLogout`. New i18n keys (12 locales):
`confirmLogoutTitle`, `confirmLogoutMessage`, `loggingOut`.

Also reset the `profileLoadedFor` guard on sign-out in
`use-session-controller.hook.ts` (stale-user hazard found during exploration).

**Tests.** ConfirmDialog busy-state unit test; new e2e `auth-flows.spec.ts`: logout shows
dialog, cancel keeps session, confirm returns to login (local mode).

## Phase 3 — Language/theme persisted per user (item 9)

**Current state (verified).** Already implemented: profile stores
`locale/theme/defaultCurrency` (`domain.types.ts:26-35`), login restores
(`use-session-controller.hook.ts:74-91`), profile wins over device (`:44-46`), saves mirror

No schema or rules changes. Add restore-path evidence: unit test for the effective-value
precedence; e2e (local mode): set dark + Arabic in settings, logout, login → dark + RTL
restored.

## Phase 4 — Settings split into subpages (item 7)

**Current state (verified).** One 170-line container renders 8 concerns; one 206-line hook
exposes 28 members; one `<form>` spans profile prefs + analytics consent. Flat route
descriptors (`AppRouteDescriptor` has no `children`) — sibling paths are the established
multi-screen pattern (orders, group-orders).

**Design.** Flat sibling routes under the settings module, hub-and-spoke:

- `/settings` — hub: profile summary card + link rows (Preferences, Privacy, Security,
  Account & data) with chevrons; each row a large touch target.
- `/settings/preferences` — name, language, theme, currency (email display stays here,
  read-only).
- `/settings/privacy` — analytics consent (Phase 6 makes it real).
- `/settings/security` — change password.
- `/settings/account` — export data, danger zone (delete account, Phase 5).

Each subpage: own container + own focused hook (decompose `use-settings.hook.ts`; the
existing `use-change-password.hook.ts` is the precedent), `BackLink` with fallback
`SETTINGS_PATH`, own submit. Route constants in
`settings-route-paths.constants.ts`; nav item unchanged. New i18n keys for hub rows and
subpage titles (12 locales). The old monolithic container/hook are deleted (no dead code).

**Tests.** New unit tests per subpage hook where logic is pure; e2e: hub navigation to each
subpage and back; the existing `/settings` touch-target sweep keeps passing (hub rows).

## Phase 5 — Delete account with re-auth (item 3)

**Current state (verified).** Text-only `ConfirmDialog`; then client-side cascade
`deleteAllUserData` → `deleteAccount` (`firestore-data.gateway.ts:222-246`,
`firebase-auth.gateway.ts:98-103`). No reauth — Firebase throws `requires-recent-login`
for stale sessions, and the hook's handling branch is dead because the error translator
rewrites messages first (`use-settings.hook.ts:163`). Local mode verifies nothing. The
firebase facade already exports `EmailAuthProvider` + `reauthenticateWithCredential`;
`changePassword` (`firebase-auth.gateway.ts:68-84`) is the working reauth precedent; local
records hold `passwordHash`/`passwordSalt` with a private `matchesRecordPassword` helper.

**Design.**

1. Contract: add `reauthenticate(user: AuthUser, email: string, password: string):
   Promise<void>` to `auth-service.interfaces.ts`.
   - Firebase impl: credential from the *entered* email + password,
     `reauthenticateWithCredential`; entered email must equal the signed-in email
     (case-insensitive) before calling Firebase, so the dialog's "re-type your email"
     contract is enforced in both modes.
   - Local impl: email equality + `matchesRecordPassword` (export or reuse in-module).
2. New `src/shared/ui/danger-reauth-dialog/` (component/container/hook/index): danger-styled
   dialog with warning copy, email field, `PasswordField`, inline error slot, busy state,
   confirm disabled until both fields non-empty. All copy via props.
3. Flow in the account subpage hook: step 1 danger `ConfirmDialog` (existing copy) → step 2
   `DangerReauthDialog` → `reauthenticate` → on success `deleteAllUserData` →
   `deleteAccount` → toast. Wrong credentials render inline in the dialog, not a toast.
   Remove the dead `requires-recent-login` branch (reauth makes it unreachable by design).
4. New i18n keys (12 locales): `deleteAccountReauthTitle`, `deleteAccountReauthWarning`,
   `deleteAccountConfirmEmail`, `deleteAccountWrongCredentials`, `deletingAccount`.

**Tests.** Unit: local `reauthenticate` success/wrong-password/wrong-email
(`localServices.test.ts`); component test for the dialog; e2e (local mode): delete flow
requires matching credentials, wrong password blocks, success lands on login with data gone.

## Phase 6 — Real privacy controls (item 8)

**Current state (verified).** The 4-tier analytics consent radio persists to device
preferences and gates a rigorous, PII-redacting telemetry module
(`src/modules/telemetry`, ~570 lines) — which has **zero producers and zero sink**. No
cookies exist anywhere. Consent is device-local (does not roam). UI copy claims recording
that never happens.

**Decision.** Make it real, not remove it: the telemetry module is production-quality and
the user asked for "wired with real impact". No vendor SDK may be invented (open critical
fact in BOOTSTRAP); the sink stays on-device and privacy-safe.

**Design.**

1. Sink: `src/modules/telemetry` gains a persisted ring buffer (capped ~200 events) via a
   storage adapter (platform preferences/web storage), replacing the inert recorder as the
   default `AnalyticsService`.
2. Producers (operational tier): app-level error boundary reports, unhandled service
   failures surfaced through the session toast path, and the existing dead-declared events
   where flows already exist (`repeat_selection_used` on order repeat; session-created,
   order-placed outcomes). Product-tier: screen-view events from the app layout route
   effect. All calls go through `createTelemetryEvent`, which already returns `null` when
   consent disallows the purpose — `denied` genuinely records nothing.
3. Consent roams: add optional `analyticsConsent` to `UserProfile`, both data gateways,
   `validProfile()` in `firestore.rules` (allow-list the 4 values, tolerate absent), and the
   settings privacy subpage reads/writes profile-first with device fallback (mirroring the
   locale/theme pattern). Rules change ⇒ emulator tests updated.
4. Diagnostics transparency: the privacy subpage shows a count of locally recorded events
   and a "clear diagnostics" action; the data export includes the buffer. Copy rewritten
   (12 locales) to describe exactly what is recorded and where it lives (on device only).

**Tests.** Unit: ring-buffer sink (cap, clear, consent-off records nothing); rules test for
`analyticsConsent` validation; e2e: switching consent to `denied` stops the counter from
growing across an instrumented action, clear empties it.

## Phase 7 — Bucket as template: reorder without duplication (item 1)

**Current state (verified).** "(copy)" comes from exactly one site:
`buildDuplicateBucketDraft` (`bucket.helper.ts:66-88`, suffix at `:70`), triggered by the
Duplicate icon on owned bucket cards. "Repeat order" already clones the order (not the
bucket) with no rename, but notifies nobody. The intended template model already exists:
**ADR-0009 order sessions** — complete contracts, state machine, dual gateways, cloud
callables (`orderSessionsV170.ts`), routes (`/sessions/new/:menuTemplateId`), and a
finished create-form hook — but no UI entry point links to it, and
`createOrderSessionV170` seeds participants from active bucket members *without notifying
them*. The v1.3 flow leaves buckets in terminal `ordered` state; sessions have their own
lifecycle and do not depend on that transition.

**Design.** Wire the intended architecture instead of green-fielding:

1. **Entry points.** "Start order round" (Repeat/RotateCcw icon + label) on owned bucket
   cards and on the bucket collaborate screen for roles allowed to place group orders;
   both navigate to `ORDER_SESSION_NEW_PATH` for that bucket. On the order details screen,
   group orders' "Repeat order" gains a sibling "Start new round" action routing to the
   same session-create screen for the source bucket (personal repeat stays unchanged).
2. **Notify the same people.** New `NotificationKind` `'session_opened'` in both
   `notifications.types.ts` and `functions/src/notificationCore.ts`. Cloud:
   `createOrderSessionV170` fans out `writeNotifications` to seeded participants (route:
   the session details path). Local: `local-order-session.gateway.ts` calls
   `pushLocalNotification` for parity. i18n for the notification title/message templates
   follows the existing notification content pattern.
3. **No more "(copy)".** `buildDuplicateBucketDraft` keeps the exact title (drop the
   suffix parameter); `copySuffix` key removed from all 12 shared locales; duplicate
   remains available as an explicit "make an editable copy" affordance.
4. **Session flow completeness check.** The session details/participation screens exist;
   during implementation, any gap that blocks the happy path (open → members contribute →
   submit) is closed as part of this phase, with the ADR-0009 state machine as the source
   of truth. Findings are recorded honestly in the phase commit and release notes.

**Tests.** Update `bucket-pricing.spec.ts:105-118` (duplicate keeps exact name; two
buckets may share a title) and keep `order-lifecycle.spec.ts:244-257` green. New unit
tests: duplicate-draft title equality; session-created notification fan-out (local
gateway). New e2e: owner starts a round from a shared bucket → session created in
`collecting` with participants seeded; member sees an in-app notification (local mode).
Functions test: fan-out writes one notification per participant, none to the organizer.

## Phase 8 — Per-component skeletons (item 5)

**Current state (verified).** One fixed `Loading` primitive; 17 containers early-return it
whole-page. Buckets already runs two independent cursor pages but collapses their loading
states; dashboard/social gate many sections behind one fetch; notifications panel has no
loading state.

**Design.** New `src/shared/ui/skeleton/` primitive: `variant: 'text' | 'card' | 'row' |
'stat' | 'circle'`, `count?`, sized by CSS tokens, `aria-hidden` inside a labelled
`role="status"` region wrapper (`SkeletonSection`). Shimmer reuses the existing
`loading-shimmer` keyframes. Adoption, per screen, replacing whole-page gates:

- **Dashboard:** header renders immediately; stat grid shows 6 stat skeletons; recent
  orders shows row skeletons. `getDashboard` splits into `getDashboardStats` +
  `listRecentOrders` behind the existing contract (both gateways), so the two sections
  resolve independently.
- **Buckets:** filters + headings render immediately; owned and shared sections each use
  their *own* cursor-page loading flag with card skeletons.
- **Orders:** search/filter bar renders immediately; list shows row skeletons.
- **Social:** hero renders immediately; each of the seven sections gets its own skeleton
  and populates as the overview resolves (single fetch retained; sections stop blocking
  each other visually).
- **Notification panel:** loading state (3 row skeletons) on first subscribe.

Full-page `Loading` remains only for route guards and detail screens whose entire body is
one entity.

**Tests.** Skeleton unit test (variants, count, a11y contract). e2e: dashboard shows the
stat skeleton region before data resolves (local mode is fast — assert via an initial
`route.fulfill` delay or presence check immediately after navigation), and the existing
suites stay green (the ux-polish overflow sweep covers the new blocks).

## Phase 9 — OS notification mirroring + permissions (item 6)

**Current state (verified).** Zero OS-notification code; in-app center polls a callable
every 15 s (cloud) or listens to storage events (local); `AppNotification.route` already
carries the tap destination; `notificationOpenSequence` router-state is required for
re-tap refreshes. Firebase's npm bundle already includes messaging (unused). Android
manifest has only INTERNET; Capacitor config lists only Keyboard/StatusBar plugins.

**Design.** Foreground mirroring (in-app center → OS tray) with permissions — no FCM:

1. **Plugin (native):** `@capacitor/local-notifications` via the mandated process —
   registry entry first, `src/packages/capacitor-local-notifications` facade, consumed
   only by platform adapters. `cap sync` adds `POST_NOTIFICATIONS` (Android 13+); the
   synced native diff is committed and the security audit/capability map updated.
2. **Platform adapters** (`src/platform/device/`): `notification-permission.adapter.ts`
   (`queryPermission`, `requestPermission` — native plugin on native, web `Notification`
   API via a `src/platform/browser` wrapper; no-op "denied" when unsupported) and
   `tray-notification.adapter.ts` (`showTrayNotification({id, title, body, route})`,
   `subscribeToTrayNotificationTaps(listener)` — native `localNotificationActionPerformed`
   listener; web `Notification.onclick`).
3. **Wiring:** in `use-app-layout.hook.ts` (the notification-subscription owner), diff
   incoming notifications against the previous list; new unread items while permission is
   granted → `showTrayNotification`. Tap → navigate to `notification.route` with the
   `notificationOpenSequence` state shape and mark read. Web-tab focus guard: only mirror
   when the document is hidden (platform visibility adapter) so users aren't double-notified
   while looking at the app.
4. **Permission UX:** first login (once per device, `ui:notif-permission-asked` flag) shows
   a small pre-permission dialog explaining the value, then triggers the real prompt;
   settings → preferences gains a "Notifications" row showing current state with an
   enable action. All copy ×12 locales.
5. **Docs:** native security audit, capability map, package-wrapper status, and an
   operations note listing the FCM prerequisites (VAPID key, `google-services.json`,
   APNs/`GoogleService-Info.plist`) for future background push. iOS code paths ship but
   are recorded as unvalidated (EXC-5).

**Tests.** Unit: permission adapter fallback logic (unsupported → denied, never throws);
mirroring diff logic (only new unread items fire, focused-tab suppression). e2e: with
`Notification` stubbed granted, a seeded incoming notification calls the tray API (assert
via an exposed test hook/spy on the stub) — keep it Chromium-only if WebKit stubbing is
unreliable; cross-browser suite must stay green with the feature silently degraded.

## Phase 10 — Per-page tutorials (item 10)

**Current state (verified).** No tour/onboarding code; no portal (react-dom not in the
package registry); native `<dialog>` top layer cannot spotlight page elements; highest
app-shell z-index is 90; `ui:` preference namespace + sidebar-collapsed flag is the
"remembered choice" precedent; pointer-down subscription adapter exists for dismissal.

**Design.** Portal-free spotlight tour, `src/shared/ui/feature-tour/`:

- Fixed-position overlay at `z-index: 95` (below nothing it needs to cover; above panel 90)
  rendered inline at the end of the page container — no portal needed because `position:
  fixed` escapes layout, and the app shell creates no transform-based containing blocks
  (verify during implementation; if one exists, restructure that style, not the rule set).
- Spotlight = a fixed div matching the target's `getBoundingClientRect()` (ref-based
  measurement in the hook — no `document.querySelector`) with an oversized
  `box-shadow: 0 0 0 100vmax rgb(20 12 6 / 55%)` scrim and a border ring; RTL-safe logical
  positioning for the tooltip card (step title, body, step dots, Next/Skip/"Don't show
  again" checkbox).
- `use-feature-tour.hook.ts` per page: takes an ordered list of `{key, targetRef}` steps;
  handles resize/scroll re-measure via a new `src/platform/browser` observer adapter;
  Escape and scrim click end the tour; completion or "don't show again" writes
  `ui:tour:<page>` via the preferences adapter; the tour auto-opens only when the flag is
  absent.
- Pages and steps (2–3 each, keys ×12 locales): dashboard (stats, recent orders, nav),
  buckets (create, duplicate/start-round actions, sections), orders (search, order row),
  social (find friends, groups), settings hub (rows). A "Replay tutorial" row in settings
  → preferences clears the flags.
- Reduced-motion: no animated transitions when `prefers-reduced-motion` (existing platform
  media-query adapter or a small addition).

**Tests.** Unit: tour hook state machine (open only when flag absent, step advance,
dismiss persistence). e2e: first visit shows the dashboard tour, "don't show again"
persists across reload, replay from settings re-opens it; a11y — focus lands on the
tooltip card, Escape closes.

## Phase 11 — Icon and UX polish (item 11)

**Design (bounded).** Informed by the exploration reports and the browser UAT pass:

- Every icon-only button gains a visible-on-desktop tooltip (`title`) and consistent
  `aria-label` (already mostly present; sweep and close gaps).
- Ambiguous actions get paired text labels where space allows (e.g. "Start order round"
  never icon-only on desktop; bottom-nav labels stay).
- Icon audit: replace low-affordance glyphs flagged during UAT (candidates: Duplicate
  `CopyPlus` vs Start-round `RotateCcw`/`Repeat` distinction must be visually obvious);
  new icons go through `src/packages/icons/index.ts` only.
- Empty states: ensure each list screen's `EmptyState` has an action button leading to the
  natural next step (create bucket, browse buckets, find friends).
- Touch targets: keep the ux-polish ≥44px sweep green over all new UI.

No blanket redesign; every change is individually small, localized, and covered by the
existing e2e polish suites.

## Cross-cutting engineering rules applied to every phase

- New strings: keys in **all 12 locales** of the owning catalog; `npm run i18n:check` gates.
- New files: kebab-case + responsibility suffixes; hooks only in hook files; components
  hook-free; declarations in `*.types.ts`/`*.constants.ts`/`*.interfaces.ts`/`*.enums.ts`.
- Browser/device APIs only via `src/platform`; vendors only via `src/packages` facades
  (registry entry before first import).
- Firestore rules changes (Phase 6) ship with emulator denial/success tests.
- Per phase: targeted tests → `lint:fix`/`lint` → both typechecks → focused unit/e2e →
  conventional commit → push → Branch Continuous Release ladder green before the next
  phase begins (gates traced via `gh run watch`/`gh run list`).
- Docs updated with the behavior they describe (architecture/context/skills/migration
  tables, native security audit for Phase 9); `.ai/` rebuilt via
  `npm run knowledge:build:incremental`, never by hand.
- Release wrap-up: `release-notes/v1.8.0.md` highlights verified behavior only; CHANGELOG
  bullets appended; `.env.example` gains `CONTACT_EMAIL_PROVIDER` (drift found in audit);
  final ladder per `skills/versioning/SKILL.md` §3 including `test:rules`,
  `functions:validate`, full e2e matrix, `security:audit`, `cap:sync`.

## Risks and mitigations

| Risk | Mitigation |
|------|------------|
| Session flow has unshipped gaps beyond the entry point (Phase 7) | Timebox a completeness audit at phase start; close happy-path gaps only; record the rest honestly in release notes |
| `(copy)` removal breaks pricing e2e | Tests updated in the same commit; duplicate semantics otherwise unchanged |
| New Capacitor plugin alters native builds | Follow add-capacitor-plugin skill; commit synced `android/` diff; Android smoke via local SDK; iOS recorded as pending (EXC-5) |
| Notification mirroring double-notifies | Visibility-gated mirroring; diff-based (only new unread) |
| Firestore rules tightening (`analyticsConsent`) rejects legacy profiles | Field optional; validator tolerates absence; emulator tests cover both |
| Settings split breaks deep links/tests | Old `/settings` remains the hub (no removed route); e2e sweep updated |
| Per-phase push cost (90-min branch CI each) | Acceptable: user explicitly required per-phase push + gate tracing |
