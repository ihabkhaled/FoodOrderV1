# v1.11.0 tap-count walkthrough

Manual browser evidence for the phase A–G simplifications, measured against
the actual pre-release code (commit `8170e63`, the v1.10.1 state this
release branched from) rather than from memory or the release notes'
narrative. Every "before" claim below is read from that commit's source;
every "after" claim was walked through live in a browser against the
current build at 390×844.

## 1. Reaching Settings (and every other primary destination)

**Before:** the bottom bar rendered 8 items in this order: Home
(marketing site), Dashboard, Buckets, Members, Orders, Settings, About,
Contact — confirmed in `8170e63`'s `bottom-nav.component.tsx` and
`public-nav-links.helper.ts`. Each item had a fixed `min-width: 68px`
(`8170e63`'s `styles.css`). At 390px width the bar's own CSS caps it to
`min(440px, 100% - 24px)` = 366px; 8 items at 68px plus gaps and padding
need roughly 586px — more than the full viewport width, let alone the
capped bar — so the row scrolled horizontally and only its first ~5 items
were visible without a swipe. **Settings sat 6th of 8**, past that fold.

**After:** exactly 5 fixed items — Home, Menus, Rounds, Members, Settings —
confirmed live: `nav.scrollWidth` (361px) is smaller than the bar's own
width (363px), so `overflows: false` at 390px. Every one of the 5 is
reachable in **1 tap, 0 scrolling**, verified by clicking each and reading
the resulting URL (`Rounds` → `/en/sessions`, `Settings` → `/en/settings`).

**Trade-off, stated plainly:** About and Contact moved out of the bottom
bar into Settings. Reaching them is now Settings (1 tap) then the link (1
tap) — 2 taps instead of a single tap *if* they happened to already be
scrolled into view, which they usually weren't. This is a deliberate cost
on the two least-used destinations to make the five most-used ones always
visible and never require a scroll gesture — the trade this release set out
to make, not a free win.

## 2. Finding "Rounds" (order sessions) at all

**Before:** `order-sessions` had a mounted route in `8170e63` but no entry
in `NAV_ITEMS` or anywhere else in the primary navigation. The only way in
was a deep link or an in-context action from a specific bucket (e.g.
"Start round"). A person who wanted to see all their rounds, or didn't
already have a bucket to start one from, had no path there at all.

**After:** "Rounds" is the 3rd of 5 fixed bottom-nav items. Verified live:
one tap from the dashboard lands on `/en/sessions`.

## 3. Sharing a menu: getting a link, checking members, checking activity

**Before** (`8170e63`'s `group-orders.routes.tsx` and
`bucket-share.container.tsx`): three separate routes —
`buckets/:id/share`, `buckets/:id/share/members`,
`buckets/:id/share/activity` — each a full page load. On the main share
page, the join-code panel (`BucketInvitePanel`) was imported and rendered
*before* the shareable-link panel (`BucketInviteLinkContainer`), so the
harder-to-use option (a code someone has to type in) came first.

**After**, walked through live end to end on a fresh bucket: opening
`/share` shows the shareable link panel first — "Share link" / "Invite by
link" — with the join code demoted into a closed `Other ways to invite`
section below it. `Members (1)` and `Activity` are two more closed
sections on the *same* page, each one tap to expand — no navigation, no
page reload. Confirmed via the actual `<details open>` state: all three
start closed, and expanding any one of them doesn't change the URL.

Net effect: seeing all three (link, members, activity) was 3 page loads
before; it's 1 page load plus up to 2 in-page taps now, and the one thing
most people actually came for — a link to send — needs no expansion at
all.

## 4. A brand-new account's first look at the dashboard

**Before:** the dashboard eyebrow always read "Welcome back" and the intro
line always described "what is open right now and what recently closed" —
copy written for someone with an order history, shown unconditionally to
someone who had registered thirty seconds earlier and had neither.

**After** (this release's own gap, closed alongside this walkthrough):
verified live by registering a fresh account — the dashboard reads
"Welcome!" and "Let's create your first menu — add a few items, then
invite people or place an order." Creating that first menu and returning
to the dashboard flips it back to "Welcome back" and the normal activity
summary, confirmed live and locked in by
`tests/e2e/dashboard-first-run.spec.ts`.

## 5. Understanding a permission role (not a tap count, but zero-lookup)

**Before:** a shared menu's member list showed the role nouns
"Contributor", "Editor", "Viewer", and a "Revoke" action — words that name
a category rather than say what happens.

**After:** "Can order", "Can change the menu", "Can only look", "Remove
access" (Phase A). This isn't a tap saved, it's a lookup avoided — nobody
has to guess what "Contributor" lets them do.

## Summary

| Flow | Before | After |
| --- | --- | --- |
| Reach Settings | 6th of 8 scrolling items, swipe likely needed | 1 tap, always visible |
| Reach Rounds | no nav entry — deep link or via a bucket only | 1 tap, always visible |
| Reach About/Contact | 1 tap if scrolled into view (7th/8th of 8) | 2 taps, via Settings |
| See a menu's share link, members, and activity | 3 page loads, join code shown first | 1 page load, link shown first, 2 optional in-page taps |
| First-time dashboard | "Welcome back" + irrelevant activity summary | "Welcome!" + a first-menu prompt |
