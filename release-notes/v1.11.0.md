# FoodOrderV1 v1.11.0

Plain language, five visible destinations, and an interface sized for someone
reading a phone without glasses.

## Highlights

### Phase A — it is a menu, not a bucket

- **Six of thirteen languages showed users a transliteration of English
  jargon.** `बकेट`, `バケット`, `บัคเก็ต` carry no meaning in Hindi, Japanese
  or Thai; French called it a shopping basket (`Paniers`) and Italian left it
  in English. Meanwhile the tours, the marketing site and all six guides
  already said "menu", so the product spoke two languages about its own
  central object. Every locale now uses its own natural word.
- Where that word is grammatically gendered the replacement keeps the gender
  (Spanish `carta`, German `Speisekarte`), so surrounding articles stay
  correct. That is why this shipped as an explicit table rather than a
  find-and-replace.
- **Permission levels now say what a person can do**: "Can order", "Can
  change the menu", "Can only look", "Remove access" — replacing
  Contributor, Editor, Viewer and Revoke. Role nouns are worse than jargon,
  because "Contributor" looks like a word the reader should already know, so
  they do not ask.

### Phase B — five destinations, and text you can read

- **The bottom bar had grown to eight items and scrolled sideways.** A
  navigation bar that scrolls hides options from exactly the person least
  likely to find them by swiping. It is now five, all visible at once on a
  390px phone: Home, Menus, Rounds, Members, Settings.
- **Rounds gained an entry point it never had**, despite being the feature the
  product is built around. Orders lost its own tab: the home screen already
  lists recent orders, and an order is reached through the menu or round it
  belongs to. Home, About and Contact moved into Settings.
- **Text now has a floor**: body 16px, nothing below 13px, targets at least
  48px. Measured in a browser at 390px — navigation labels went from
  **10.56px to 13.12px**, smallest target **47px to 51px**, and there are now
  **zero elements under 13px** on the signed-in page.

### Phase C — one screen for sharing, not four

- **A menu had seven pages of its own**; three of them were about sharing.
  Members and Activity are now collapsible sections of the Share page, closed
  by default so the page still opens on the thing most people came for.
  Reading a person's permissions no longer means leaving the screen that
  grants them.
- **Every old address still resolves.** `/share/members` and `/share/activity`
  redirect into the section that replaced them, using a fragment so the page
  scrolls to the right place. People bookmark pages and paste them to each
  other, and a link that dies teaches them not to trust the next one.
- The two superseded containers, their two tour hooks and two route builders
  were deleted rather than left behind; the dead-code gate found them.

### Phase D — help where it helps, silence everywhere else

- **Twenty-two screens had a tour, some eight steps long.** For a first-time
  visitor that is an obstacle course between them and the button they came to
  press. Five screens keep a tour and each is three steps: Home, Menus, the
  menu editor, sharing, and a round's details. Replay stays in Settings.
- **The rename had missed the modules.** Translations live in seven
  directories, not one, so group-orders still said "Freeze bucket" and social
  still said "Invite friend to bucket" after a release that was supposed to
  have removed the word. Both are rewritten in all thirteen languages, and
  "freeze" is now "stop taking orders" - it says what happens.
- **3,198 dead strings deleted.** Removing seventeen tours orphaned 246 keys
  in each of thirteen locales; they were unreferenced anywhere in source.
  Locale files went from 579 entries to 333.

### Phase E — checked, not assumed

- **Wrote a browser-based accessibility audit** (`tests/e2e/accessibility.spec.ts`)
  that walks Home, Menus, Rounds and Settings in both themes on every
  configured browser, checking real WCAG contrast math (relative luminance,
  4.5:1 body text / 3:1 large text), 44px touch targets, unlabelled form
  fields and images without `alt`, rather than relying on eyeballing a
  screenshot.
- **The light-theme brand colour failed its own contrast requirement.**
  `--primary: #ea580c` measured 3.56:1 with white ink - below the 4.5:1 body
  text needs - on the default button, the active bottom-nav pill, and the
  logo. Every darker orange on the same hue was checked with a WCAG script
  and `#c2450a` chosen: 5.06:1 solid, 4.74:1 at the far stop of the button's
  gradient, both with real margin, not a bare pass. Dark theme already paired
  a dark ink with a light primary and needed no change.
- **The bottom nav's translucent, blurred background made its own inactive
  labels' contrast unverifiable** - `color-mix(... 92%, transparent)` behind a
  `blur(14px)` filter means the true rendered colour depends on whatever the
  page happens to be scrolled to underneath it. It is opaque now
  (`var(--surface)`), giving every label a fixed, checkable pairing (measured
  9.25:1 dark, 9.3:1 light).
- **Saving any setting reloaded the whole page.** `saveProfile` always passed
  the current locale alongside whatever actually changed, and the session
  controller treated any locale value as "the locale changed" and hard-
  navigated to it - so changing only the theme or full name flashed a full
  page reload every time. It now compares against the locale actually on the
  profile before navigating; a reload only happens when the language itself
  changes.
- **The share link is now the first thing offered, not the join code.** On a
  menu's Share page, the invite-link panel renders before the join-code
  panel, which moved into a collapsed "Other ways to invite" section (new
  `otherWaysToInvite` / `otherWaysToInviteHint` keys, all thirteen locales) -
  a link a person can tap beats a code they have to retype.
- **Bare links now meet the 44px minimum too**: the brand mark (was 36x36)
  and every plain link in the topbar, page headings and section headings.
  Widening those grew some headings by a few px each, which on the
  narrowest, shortest screens this app still supports pushed the last
  section on a long page in behind the fixed bottom nav; the page's bottom
  clearance was widened to match.

### Phase F — what the code is actually for, in one place

- **Twelve of sixteen modules had a README; every package, every platform
  adapter directory, and every shared directory had none.** The gap wasn't
  the business modules people read first - it was the thirty other
  directories a new engineer has to open cold. All sixteen modules, all
  thirteen owned package facades, all six platform adapter directories, and
  all four shared directories now have one, in the same
  Responsibility / Public exports / Structure / Dependencies / Testing shape
  the existing module READMEs already used - adopted, not invented.
- **Added `docs/product/business-overview.md`**, the layer between the root
  README's elevator pitch and each module's implementation detail: domain
  object lifecycle (bucket order states, order-session trust boundary),
  bucket roles in the words shown to a person, the pricing-policy fields and
  allocation strategies, the three billing plans and where entitlement
  authority actually lives, and a one-line-per-module map. Linked from
  `AGENTS.md` and the root README rather than left to be found.
- Every fact in these 28 documents was read from the source that same pass,
  not inferred from a directory name - three parallel research passes
  covering packages, platform + shared, and the four undocumented modules
  plus `src/app/`, each instructed to report only what it actually read.

### Phase G — a first menu that's actually guided, and the numbers to prove the rest

- **A brand-new account's dashboard called them a returning user.** The
  eyebrow always read "Welcome back" and the intro line always described
  "what is open right now and what recently closed" - copy written for
  someone with an order history, shown to someone thirty seconds into their
  first session with neither. It now reads "Welcome!" and points straight
  at creating a first menu, for exactly as long as `bucketCount` is zero -
  the moment they create one, the dashboard reverts to the normal returning
  -user greeting on the next visit. Verified live end to end, then locked
  in by a new spec.
- **Wrote `docs/ux/v1.11.0-tap-count-walkthrough.md`**, the manual
  walkthrough this release's own plan called for and hadn't produced yet.
  Every "before" figure in it is read from `8170e63` (the v1.10.1 commit
  this release branched from), not from memory or the earlier phases'
  release notes - the old bottom nav's fixed 68px item width and 366px
  available width at 390px, the three separate share routes, the join-code
  panel rendered before the share-link panel. Every "after" figure was
  walked through live in a browser against the current build. It states one
  real trade-off plainly rather than only counting wins: reaching About/
  Contact went from a single tap (when they happened to be scrolled into
  view, as the 7th/8th of 8 items) to two taps through Settings, a
  deliberate cost on the two least-used destinations that bought the five
  most-used ones a guaranteed, scroll-free single tap each.

### Phase H — a className is a promise the CSS has to keep

- **Reported**: the Share page's collapsible-section titles and hints
  rendered as one run-on string - "Other ways to inviteA code they type in,
  if a link will not reach them." `<strong>` and `<span class="muted">` are
  both inline by default, and the markup added in Phase E never gave them a
  layout of their own. Fixed for every collapsible section summary in the
  app in one rule, not just the one reported.
- **Audited the rest of the app for the same class of defect** by cross-
  referencing every `className` used in JSX against every selector actually
  defined across every stylesheet - not a visual skim, a mechanical diff of
  what the code asks for against what the code provides. Found eight more,
  ranging from cosmetic to severe:
  - `.stack-xs`, referenced in 8 components across order-sessions, session-
    invites and settings, never defined anywhere - each rendered its own
    title/hint pairs, and in one case a whole form, as unspaced text.
  - `.member-count-pill` (a group's member count next to its name) never
    defined - it ran straight into the name with no space and no badge
    styling at all.
  - `.measure`, expected to give two order-session page intros the same
    readable line length `.page-intro` already builds in, never defined -
    those paragraphs ran the full width of a desktop screen.
  - `className="sr-only"` on a fieldset legend and a busy-state
    announcement - the real class in this codebase is `.visually-hidden`;
    both were rendering visibly instead of being screen-reader only.
  - **The most severe finding**: `BusyButton`'s `className` prop *replaces*
    its own `'button'` default rather than merging with it, and the invite
    -link accept button - the one control that actually redeems an invite -
    passed `className="primary"`, which is not a defined class anywhere.
    The single most important button on the `/join/:token` screen was
    rendering with no color, no padding, and no 44px touch target at all.
  - The invite-link preview card used `.card` instead of `.section-card`,
    so it had no border, background, or padding; its subject line (what a
    person is actually being asked to join) had no visual emphasis.

## Fixed

- Phase A: the new guard test caught two French and one Thai string that the
  English-derived key list had missed — they used the old word in keys whose
  English value never mentioned it.
- Phase B: navigation labels were still computing to 10.56px after the first
  pass, because eight further stylesheets overrode the one that was raised.
  The browser measurement caught it; reading the source would not have.
- Phase D: end-to-end tests asserted retired copy three separate times
  ('Bucket title', 'Bucket saved.', 'Bucket invitation sent...'), each found by
  CI minutes after a push. A tooling test now compares asserted copy against
  the strings the app actually ships, and the plain-language guard was widened
  from one locale directory to all seven - its blind spot was what let the
  module wording survive Phase A.
- Phase D: the tour test hardcoded "1 / 6" and asserted that Skip-all silenced
  Settings, a screen whose tour had been removed. It now reads the step count
  from the tour and iterates the real page list, so trimming a tour no longer
  breaks a test that has nothing to say about trimming.
- Phase D: trimming the dashboard tour left a spotlight ref with no step,
  which the lint rule caught as an unnecessary dependency; the dead state was
  removed rather than the dependency silenced.
- Phase C: the navigation bar overflowed in Firefox where Chromium fitted by a
  single pixel, because items had a fixed minimum width. They flex now, so the
  bar cannot overflow in any browser or in a language with longer words -
  German and Portuguese would have hit the same edge. Verified on chromium,
  firefox, webkit and mobile safari locally rather than by pushing again.
- Phase C: the cross-browser suites failed because `ux-polish.spec.ts` asserted
  eight navigation links and required the bar to scroll - it encoded the very
  design being replaced. It now asserts five and no overflow.
- Phase B: the architecture rule caught a helper being imported from `app`
  into a module. It moved to `public-content`, which owns knowledge of the
  public pages, rather than the rule being suppressed.
- Phase E: the audit script's own colour parser read `color(srgb r g b)` - how
  Chromium serialises a `color-mix()` result - on the same 0-255 scale as
  classic `rgb()`, whose channels are 0-1 in that syntax. It read a light,
  near-opaque background as almost black and produced a wave of contrast
  failures that were an artifact of the parser, caught by recomputing the same
  live colour independently and getting a different answer. A second parser
  gap skipped gradient-painted elements (`background-image`, not
  `background-color`) straight past to whatever solid colour sat several
  ancestors up - usually the opposite theme's page background - producing
  more false positives. Both are fixed in the audit script, not the app.
- Phase E: the audit's visibility check treated a zero-area box as visible,
  because a collapsed sidebar label's `getClientRects()` is non-empty even at
  0x0. It flagged an unreadable collapsed-sidebar duplicate of a label a
  person never sees, on every screen, in both themes. The check now also
  requires the box to have real width and height.
- Phase E: evaluating the audit immediately after navigation could sample a
  colour mid-transition - the theme applies in a post-render effect, so a
  fresh page briefly paints the other theme's colours before correcting them
  over 140ms - and flagged a blended colour nobody actually reads. The audit
  now waits for every nav link's colour and background to hold across two
  polls before reading them.
- Phase E: `responsive-navigation.spec.ts`'s scroll-to-bottom helper jumped
  once to whatever `scrollHeight` was at the moment it ran, which could be
  read before a seeded list had finished rendering in; the page kept growing
  after the jump landed and nothing scrolled again to reach it. It now
  re-scrolls on every poll and requires the document's own height, not just
  the scroll position, to hold steady twice in a row before calling the
  bottom reached.
- Phase G: `tests/tooling/release-notes-phases.test.mjs`'s phase-row pattern
  was hardcoded to `[A-F]`; it would have silently stopped validating this
  phase's own release-notes entry, and every later one, instead of failing.
  Widened to `[A-Z]`.
- Phase G: `npm audit` started failing on push, not from anything this
  phase's diff touched - four nodemailer advisories (one high, three
  moderate) were evidently published between the previous phase's green
  run and this one. `nodemailer` moved from 9.0.5 to 9.1.1, a same-major,
  in-range fix verified by the existing password-reset API test and a full
  production build.

## Not done in this release

- URLs still say `/buckets`; only the words changed, so existing links and
  bookmarks keep working.
- Phase F documented at directory granularity (module, package, platform
  adapter, shared layer) plus one business overview - it did not add inline
  comments to individual functions, which this codebase's own convention
  reserves for a non-obvious WHY, not a restatement of WHAT a well-named
  function already says.
- Phase G's new-user dashboard state is keyed on `bucketCount === 0` only;
  someone who deletes every menu they ever made would see the first-run
  welcome again. Treated as acceptable rather than fixed: it is also true
  to their account's current state, and guarding against it would need a
  separate "has ever created a menu" flag this release didn't add.
- Phase H's className-to-CSS cross-reference is a static check: it finds a
  class with zero matching selector, not a class whose selector produces
  the wrong layout. A handful of matches were judged harmless (a semantic
  hook combined with an already-correctly-styled class, e.g.
  `.invite-link-share` alongside `.section-card`) rather than given their
  own unused CSS. The most severe fix - the invite-link accept button - was
  verified by reading `BusyButton`'s prop defaults, not by completing a
  live redemption; the manual build used for the rest of this audit's
  screenshots wasn't running in local-mode, so that one screen's own
  network call failed for an unrelated, pre-existing reason (a real
  Cloud Functions CORS response, not a UI defect) before the button could
  be seen redeeming anything.
